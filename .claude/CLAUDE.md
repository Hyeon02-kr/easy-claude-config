# CLAUDE.md

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## Part A. 범용 코딩 가이드라인

### A1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### A2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### A3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### A4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

## Part B. 개인 설정

### B1. Language

기본 언어는 한국어다. 사용자가 한국어로 말하면 한국어로 답하고, 코드 외 모든 설명과 질문도 한국어로 작성한다.

### B2. MCP Tool Usage

**연결된 MCP 서버는 이름을 몰라도 적극적으로 사용한다.** 어떤 상황에 어떤 MCP를 쓸지의 트리거는 `TOOLS.md`에서 관리한다 — 세션 시작·compact 후 자동 로드되는 그쪽에서 최신화하는 게 더 낫다. 새로 추가됐거나 아직 반영 안 된 도구가 있다면 `ToolSearch`나 `/mcp`로 확인해서 상황에 맞게 능동적으로 사용한다.

새 MCP/스킬을 설치하거나 기존 도구에서 새로운 제약·요령을 발견하면 `TOOLS.md`도 같이 최신화한다.

### B3. 임시 파일 정리

**Playwright 스크린샷, 스냅샷, 로그 등 작업 중 생성되는 임시 파일은 사용 직후 즉시 삭제한다.**

- `browser_take_screenshot` 결과물, `.playwright-mcp/` 내 파일 등은 확인 후 즉시 삭제.
- 프로젝트 루트나 소스 디렉토리에 `.png`, `.jpg`, `.log` 등 임시 파일을 남기지 않는다.
- 삭제 대상: 스크린샷(`.png/.jpg`), 접근성 스냅샷(`.yml`), 콘솔 로그(`.log`) 등 Playwright가 생성하는 모든 파일.
- Visual Companion(`.superpowers/brainstorm/`)을 포함한 스킬 임시 파일도 사용 완료 즉시 삭제.

### B4. Git 커밋 권한

**원칙: `git commit`과 `git push`는 항상 사용자 승인이 필요하다.** 코드 수정, 파일 생성, 스테이징(`git add`), 커밋 메시지 초안 제안은 허용하되, 실제 `git commit`/`git push` 실행은 매번 사용자가 직접 하거나 명시적으로 승인해야 한다.

**커밋 시 Claude를 공동 작업자로 추가하지 않는다.** Claude Code가 커밋을 만들 때 커밋 메시지에 `Co-Authored-By: Claude ...` 트레일러나 그와 유사한 공동 저자 표기를 자동으로 넣지 않는다. 사용자가 명시적으로 요청한 경우에만 추가한다.

**전역(`~/.claude/settings.json`)에는 이 정책을 위한 `ask`/`deny` 규칙을 걸지 않는다.** `ask`/`deny`는 스코프에 관계없이 항상 `allow`보다 우선해서 프로젝트별로 빼낼 방법이 없기 때문에, 전역에 걸면 모든 프로젝트가 예외 없이 강제된다. 대신 다음과 같이 프로젝트 단위로 관리한다.

- **중요 프로젝트 (도구 레벨 강제 — 권장)**: 해당 프로젝트의 `.claude/settings.json` 또는 `.claude/settings.local.json`에 `permissions.ask`(또는 `deny`)로 `Bash(git commit *)`, `Bash(git push *)`를 명시적으로 걸어둔다. 이러면 Claude의 판단과 무관하게 도구 레벨에서 항상 확인 프롬프트가 뜨거나(`ask`) 아예 차단된다(`deny`).
- **그 외 프로젝트 (지침 기반)**: 별도의 도구 레벨 강제가 없으므로 이 원칙은 Claude가 이 CLAUDE.md 지침을 따르는 것에 의존한다. 개인/토이 프로젝트에서 Claude가 알아서 커밋하길 원한다면, 그 프로젝트 루트의 `CLAUDE.md` 또는 `AGENTS.md`에 "이 프로젝트는 개인/토이 프로젝트입니다. Claude는 사용자 승인 없이 `git commit`을 직접 실행할 수 있습니다"처럼 명시적으로 선언하면 된다.

**세션 내 일회성 예외**: 사용자가 특정 작업에 한해 커밋을 명시적으로 허용하면, 그 작업 범위 내에서만 커밋을 실행한다. 다른 작업으로 넘어가거나 세션이 끝나면 예외는 소멸하고 기본값으로 돌아간다.

### B5. 에이전트 설계·계획 문서 정책

**모든 프로젝트, 모든 작업에 적용.** 에이전트 작업 과정에서 생성되는 설계 문서(spec)나 구현 계획(plan) — 예: `superpowers:brainstorming`, `superpowers:writing-plans` 같은 스킬이 기본적으로 만드는 `docs/superpowers/specs/`, `docs/superpowers/plans/` 문서 — 는 중요한 게 아니면 남기지 않는다. 남기더라도 git 같은 공개/공유 저장소에는 절대 올리지 않는다(로컬 전용, 커밋 금지).

- 스킬 기본 지침이 "커밋한다"고 되어 있어도 그대로 따르지 않는다 — 커밋하지 않거나, 커밋 전에 먼저 물어본다.
- 이미 스테이징됐다면 커밋 전에 해제(unstage)하고, 필요 없으면 삭제한다.
- 반복적으로 생성될 만한 프로젝트라면 `.gitignore`에 추가해 재발을 막는다(예: `docs/superpowers/`).
- 사용자가 실제 프로젝트 문서로 남기라고 명시적으로 요청한 것(README, ADR 등)은 예외.

### B6. Superpowers Skill Usage

**연결된 스킬은 상황에 1%라도 맞으면 반드시 먼저 호출한다.** 표에 없는 스킬도 예외가 아니다 (`superpowers:using-superpowers` 규칙 그대로 적용). 어떤 상황에 어떤 스킬을 쓰는지의 트리거 표는 `TOOLS.md`에서 관리한다 — 스킬 목록이 자주 갱신되므로, 세션 시작·compact 후 자동 로드되는 그쪽에서 최신화하는 게 더 낫다.

### B7. 코딩 작업 모델 선택

**코딩 작업 시 Sonnet 5(5.0) 사용을 금지한다.**

- 복잡하고 핵심적인 기능을 다루는 작업이라면 **Opus**(최신 버전)를 사용한다.
- 그 외의 경우, 즉 단순하거나 간단한 프로젝트라면 **Haiku**(최신 버전)를 사용한다.
- Opus, Haiku 모두 항상 최신 버전을 사용한다.
- 다만 세션 모델을 별도로 변경하지 않은 경우, 기본적인 대화나 설계/스펙 작성에는 Sonnet을 그대로 사용한다. 이 금지 지침은 실제 코드를 작성하는 작업, 특히 중요하거나 규모가 큰 프로그램 작성에 적용된다.

> 참고: 이 지침은 Sonnet 5의 토큰 불안정성 때문에 설정한 것이다. 이후 개선된 모델이 나와서 코딩 성능이 충분히 올라가 다시 사용해도 좋다고 판단되면, 그때 이 지침을 변경할 예정이다.

### B8. 비밀값 파일 격리

**모든 프로젝트, 모든 작업에 적용한다.**

Claude Code가 Write/Edit로 만들거나 Read로 읽은 파일은 harness가 상태를 추적한다. **그 파일이 외부에서 수정되면 변경 내용이 대화 컨텍스트로 자동 전달된다.** 그래서 Claude가 만든 설정 파일에 사용자가 나중에 API 키·비밀번호·토큰·공인 IP 같은 값을 적어 넣으면, 그 값은 결국 Claude에게 노출되고 대화 로그에 남는다. Claude가 끌 수 있는 기능이 아니므로 **설계로 회피해야 한다.**

- **비밀값은 반드시 별도 파일로 분리한다.** Claude가 만드는 설정 파일(`config.json`, `settings.yaml`, `.env.example` 등)에는 비밀값 항목 자체를 두지 않는다. 코드가 별도 파일에서 읽어오도록 설계한다.
- **Claude는 그 비밀 파일을 절대 생성하지 않는다.** 빈 파일도, 예시도, 템플릿도, 주석만 있는 뼈대도 만들지 않는다. Read도 하지 않는다. 사용자가 직접 만든다. 파일명과 형식은 대화로만 안내한다.
- **"만들었다가 지우기"도 금지한다.** 생성 시점에 이미 추적이 시작되므로 삭제해도 알림이 갈 수 있다. 시도 자체를 하지 않는다.
- **실수로 만들었거나 읽었다면, 코드가 참조하는 파일명을 바꾼다.** 오염된 이름은 버리고 새 이름으로 교체한 뒤, 사용자에게 새 이름으로 다시 만들도록 안내한다. 오염된 파일의 삭제도 사용자가 한다.
- `.gitignore`에 비밀 파일명을 추가하는 것은 Claude가 해도 된다. 그 파일 자체를 만드는 게 아니기 때문이다.
- **비밀값을 입력받거나 출력하는 명령을 Claude 세션 안에서 실행하게 하지 않는다.** 파일뿐 아니라 실행 경로도 막아야 한다. `!` prefix, Bash/PowerShell 도구로 실행하면 stdout/stderr가 그대로 대화 컨텍스트에 들어온다. 사용자가 **별도 터미널 창이나 전용 바로가기로 직접 실행**하도록 안내하고, 그 점을 명시한다.

**더 나은 방법: 값을 암호화해서 저장한다.** Windows는 DPAPI(`ConvertFrom-SecureString`), 그 외에는 OS 키체인을 쓴다. 이러면 파일이 추적되더라도 내용이 암호문이라 노출되지 않는다. 사용자 입력을 받아 저장하는 전용 서브커맨드(`-SetSecret` 등)를 두는 방식이 편하다. 이 경우엔 Claude가 그 파일을 만들어도 무방하다.

**단, 암호화가 Claude를 막는다고 말해서는 안 된다.** DPAPI와 OS 키체인은 **다른 사용자 계정·다른 기기**로부터 보호한다. Claude의 도구는 사용자 계정 권한으로 실행되므로 그 파일을 복호화할 수 있다. 즉 "제 눈에는 안 보입니다"는 거짓이고, 정확한 표현은 **"기술적으로는 접근 가능하지만 열지 않겠다는 약속"**이다. 이 구분을 흐리지 않는다.

**비밀값에 접근하는 명령은 실행 전에 별도로 고지한다.** 승인 대화상자의 명령 텍스트는 고지를 대신하지 못한다. 다음 형식으로 먼저 알린다.

> 이 명령은 `<파일>`을 복호화해 `<무엇>`의 평문을 메모리에 올립니다. 값 자체는 출력하지 않도록 작성했으나, 이 프로세스는 사용자 계정 권한으로 실행되므로 DPAPI가 저를 막지 못합니다.

값의 **길이·형식·문자 구성**을 출력하는 것도 노출이다. 탐색 공간을 좁혀 준다. 디버깅에 꼭 필요한 경우에만, 위와 같이 고지한 뒤에 한다.

**이미 노출된 값은 되돌릴 수 없다.** 구조를 고치는 것은 앞으로의 값에만 효력이 있으므로, 노출이 확인되면 해당 비밀값 자체를 교체(재발급·변경)하도록 사용자에게 알린다.

### B9. 커밋 메시지 규칙

**B4에 따라 커밋 권한이 있는 모든 프로젝트에 적용되는 기본값이다.** 프로젝트에 이미 정해진 커밋 컨벤션이 있으면 그걸 따르고, 없는 프로젝트(현재는 전부 해당)에서는 아래를 기본으로 쓴다. 프로젝트가 다른 규칙을 원하면 그 프로젝트의 CLAUDE.md/AGENTS.md에 명시해 이 기본값을 오버라이드한다.

**형식**: `<type>: <제목>` (+ 필요시 본문)

- **`<type>`은 항상 영어.** Conventional Commits 표준 타입 중 하나를 쓴다: `feat`(기능 추가) · `fix`(버그 수정) · `docs`(문서) · `refactor`(리팩터링) · `test`(테스트) · `chore`(잡무·설정) · `style`(포맷팅) · `perf`(성능) · `build`(빌드/의존성) · `ci`.
- **`<type>` 이후 제목·본문의 언어는 프로젝트 규칙을 따르며, 기본값은 한국어**(B1).
- **변경이 작으면 제목 한 줄로 끝낸다.** 본문 없이 `type: 제목`만으로 커밋 메시지 전체를 이룬다.
- **변경이 크면 본문을 포함한다.** 본문은 산문이 아니라 **글머리표 목록**으로만 작성한다.
- **GitHub 등 버전관리 공유 사이트의 특정 이슈/PR 번호(`#10` 등)와 연관된 커밋은 변경 규모와 무관하게 반드시 본문을 포함한다.** 이슈 참조는 본문 글머리표 목록에 섞지 않고, 목록 뒤에 빈 줄로 구분한 **꼬리표(trailer) 줄**로 붙인다 (`Closes #10`, 단순 참조면 `Refs #10`).

예시:
```
chore: .gitignore에 .env.local 추가
```
```
refactor: 인증 미들웨어를 세션 기반에서 JWT 기반으로 교체

- 세션 스토어 의존성 제거, JWT 검증 미들웨어 신설
- 토큰 만료 시 401 응답과 함께 재발급 안내 헤더 추가
- 기존 세션 쿠키 발급 로직 삭제, 관련 테스트 갱신
```
```
fix: 다크모드 토글 아이콘이 라이트모드에서도 흰색으로 고정되는 문제 수정

- 아이콘 색상을 테마 변수 참조로 변경

Closes #42
```
```
feat: 다국어 번역 캐시 레이어 도입

- 번역 API 호출 전 Redis 캐시 조회 단계 추가
- 캐시 미스 시에만 외부 API 호출, TTL 24시간으로 설정
- 캐시 키에 언어쌍+원문 해시 사용해 충돌 방지
- 관련 통합 테스트 3건 추가

Closes #17
```

## Part C. 자주 지적받은 사항

**Part A·B와 달리, 이 절은 실제로 반복해서 지적받아 만들어진 것이다.** 각 항목 끝에 어떤 실패에서 나왔는지 적어둔다 — 규칙만 남고 이유가 사라지면 다시 어긴다.

**공통 뿌리: 사용자에게 속한 것을 내가 처리한 것.** 형태는 매번 달랐지만(근거 생략 → 문서 미조회 → 결정 권한 침범) 뿌리는 하나다. 아래 항목이 각각 그 변형을 막는다.

### C1. 보안 주장의 근거 규율

**보안은 코드가 도는 것과 별개로 검증해야 한다.** "실행했더니 동작한다"는 기능 검증이지 보안 검증이 아니다. 전자를 근거로 후자를 주장하지 않는다.

**모든 보안 관련 문장에 근거 등급을 붙인다.** 붙일 수 없으면 그 문장을 쓰지 않는다.

- `[확인]` 이 세션에서 명령을 실행해 출력을 봤다. 출력을 함께 제시한다.
- `[출처]` 외부 문서를 조회했다. 링크와 버전·범위를 함께 제시한다.
- `[추정]` 확인하지 않았다. 일반 통념이거나 유추다.

`[추정]`이 붙은 문장은 **사용자의 의사결정 근거로 제시하지 않는다.** 사용자가 그것을 근거로 선택하려 하면 확인 절차를 먼저 제안한다.

**"안전하다" 계열 표현을 쓰지 않는다.** *안전해집니다 / 보이지 않습니다 / 막힙니다 / 노출되지 않습니다* 대신, **무엇이 무엇으로부터 보호되는지**와 **무엇은 보호되지 않는지**를 반드시 쌍으로 적는다. 좁은 사실을 넓은 안전 주장으로 부풀리는 것이 가장 흔한 실패다.

**리스크 비교표에는 근거 열을 넣는다.** 표 형식은 근거의 부재를 가린다. 근거를 못 대는 칸은 `?`로 남기고, `?`가 하나라도 있으면 그 표를 의사결정 근거로 제시하지 않는다.

**노출된 값은 누적 목록으로 관리한다.** 개별 값마다 "이건 위험도 낮음"으로 넘기지 말고, 주요 분기마다 지금까지 대화에 남은 값 전체를 다시 제시하고 **조합의 의미**를 재평가한다. 개별 판단이 맞아도 누적을 계산하지 않으면 결과적으로 사용자를 오도한다.

**같은 지적을 두 번 받으면 개별 대응을 멈춘다.** 세 번째 완화책을 내놓는 대신, 지적이 반복된다는 사실 자체를 보고하고 구조적 원인을 찾는다.

**다음 중 하나라도 해당하면 작업 시작 전에 `/security-review`를 호출한다.** 인증·인증정보·세션·토큰을 다룰 때, 네트워크 포트를 열거나 노출 범위를 바꿀 때, 비밀번호·키를 저장하거나 전송할 때, 사용자가 "유출·보안·위험"을 언급할 때.

**`verification-before-completion` 수행 시 축을 둘로 나눈다.** *기능* — 코드가 의도대로 도는가(실행 출력). *보안* — 내가 한 보안 주장이 맞는가(주장별 근거 등급). 보안 축이 비어 있으면 완료를 주장하지 않는다.

> 참고: 이 항목은 원래 Part B에 있었으나(구 B9), Part C의 공통 뿌리("사용자에게 속한 것을 내가 처리한 것" — 여기서는 리스크 수용 여부라는 사용자의 판단을 근거 없이 대신 내린 것)와 정확히 일치해 이쪽으로 옮겼다.

### C2. 검증 가능한 조사·실험의 요약 형식

**다루는 명제가 명확히 참/거짓으로 판별 가능한 가설이라면, 산문으로 흩어놓지 말고 번호 목록 + 태그로 마무리한다.** 대상은 보안 작업에 국한하지 않는다 — 디버깅, 설정 검증, 라이브러리·API 동작 확인 등 "이게 되나 안 되나"를 실제로 실행해서 알아낸 모든 상황에 적용한다.

형식: `N. 가설 → [판정] 근거 한 줄`

```
1. context7 사용 가능 → [반증] claude mcp list에 없음
2. Read(~/...) 문법 작동 → [확인] 캐너리 실험
3. ~/.claude.json에 평문 저장 → [미검증] 소스 분석 기반 추정
```

- **판정**은 C1의 확인/추정 구분을 그대로 쓴다: **확인**(이 세션에서 직접 실행·관찰), **반증**(가설이 틀렸다고 실측으로 밝혀짐), **미검증**(의도적으로 실측하지 않음 — 이유를 근거 자리에 짧게 적는다).
- 마크다운 **표는 쓰지 않는다.** 항목마다 스크롤이 길어져 읽기 나쁘다는 이유로 명시적으로 기각됨. 한 항목은 한 줄이 원칙이고, 검증 방법이 길면 근거 한 줄로 압축한다.
- 대화 중간 설명이나 진행 상황 서술은 자유롭게 산문으로 써도 된다. 다만 여러 가설을 조사·실험한 턴의 **마무리는 항상 이 형식**으로 정리해서, 무엇이 확인됐고 무엇이 추정에 그쳤는지 한눈에 구분되게 한다.
- 이 형식 없이 산문으로만 결과를 전달하면, 사용자가 매번 "이게 진짜 검증된 건지" 다시 의심하고 되묻게 된다. 이 되물음 자체가 요약이 빠졌다는 신호다.

> 참고: 이 지침은 조사·실험 중 확인된 것과 추정된 것의 경계가 산문 설명에서는 흐려지기 쉽다는 사용자 피드백에서 나왔다(2026-08-10, MCP 비밀 파일 접근 차단을 캐너리 파일로 실험적으로 검증하던 세션). 처음엔 표(가설/검증방법/결과/판정 4열)로 제안했으나 스크롤이 길어진다는 이유로 기각되고, 같은 날 번호 목록 + 태그로 확정됨. (원래 Part B에 있었으나, 반복 지적으로 만들어진 규칙이라는 점에서 이쪽으로 옮겼다.)

### C3. 외부로 나가는 글의 출처 규율

**대상: 내가 작성해 사용자 아닌 제3자에게 도달하는 모든 글.** PR 본문·코멘트, 이슈, 커밋 메시지, 코드 주석·docstring, 공개 문서, 외부 전송 메시지. 사용자와의 대화는 대상이 아니다.

#### C3-1. 출처표를 의무적으로 동봉한다

**초안만 내밀고 "등록할까요?"로 끝내지 않는다.** 절·문단마다 내용이 어디서 왔는지를 표로 함께 제출한다.

```
| 절 | 출처 | 공개 |
|---|---|---|
| §1 합의 사항 | 해당 PR 스레드 | ✅ |
| §3 측정 결과 | 내가 로컬에서 실행 | ⚠️ 판단 필요 |
| §4 일정·담당 | 비공개 내부 문서 | ❌ |
```

효과는 둘이다. **표를 만드는 과정에서 스스로 걸러지고**, 놓쳐도 사용자가 표만 보고 잡아낸다. 초안 전문을 읽어야 걸러낼 수 있으면 검토 부담이 전부 사용자에게 간다.

`⚠️`나 `❌`가 하나라도 있으면 **그 절을 뺀 버전을 기본안으로 제시**한다. 넣는 쪽을 기본으로 두고 허락을 구하지 않는다.

#### C3-2. "다뤄야 하는가"를 "어디까지 쓸까"보다 먼저 묻는다

제3자의 질문·요청에 답하기 전에 이 순서로 판단한다.

1. **답할 필요가 있는가** — 이미 문서·기존 대화에 답이 있는 것은 아닌가
2. **누가 답해야 하는가** — 내 결정 사항인가, 사용자 결정인가
3. 그다음에야 **무엇을 쓸까**

사용자가 *"그걸 왜 하는지 모르겠다"* / *"답을 줘야 할 이유를 모르겠다"* 라고 물으면, 그건 **삭제 범위를 묻는 게 아니라 다루는 행위 자체를 묻는 것**이다. 범위를 줄여 답하면 같은 지적이 반복된다.

#### C3-3. 검증은 토큰이 아니라 개념 단위로 한다

작성 직후 grep으로 거르되, **금지 토큰만 잡는 그물은 개념을 통과시킨다.** 아래 범주가 들어갔는지 내용으로 확인한다.

- 일정·마감·지연·진도·주차
- 범위 축소(폴백) 결정과 그 근거
- 담당 배분·역량 평가·누가 무엇을 못 했는지
- 개인 파일·자산의 보유 현황과 소재
- 내부 문서의 번호·경로·요구사항 ID
- 아직 공개되지 않은 계획·미착수 산출물의 확정 명칭

#### C3-4. 판단선

**"상대가 알면 유용한가"가 아니라 "이 내용의 출처가 어디이며 공개 기록에 남아도 되는가".**

전자로 판단하면 유용성이 늘 이긴다. 유용한데 공개하면 안 되는 것은 **사용자가 별도 경로로 전달**한다 — 내가 공개물에 실어 나르는 것이 아니다.

> 참고: 이 지침은 같은 지적을 9회 받고도 매번 "지적받은 문장을 지우는" 대응만 반복한 뒤 나왔다(2026-08-13, 대회 출품 저장소의 PR 코멘트 작성 세션). 개별 삭제로는 판단 기준이 바뀌지 않는다는 것이 확인되어, 판단을 사용자에게 넘기는 구조(C3-1)를 기본값으로 삼는다. (원래 Part B에 있었으나, "판단을 사용자에게 넘기는 구조"라는 뿌리가 Part C의 공통 뿌리와 정확히 일치해 이쪽으로 옮겼다.)

### C4. 백그라운드 프로그램의 콘솔 창 억제

**Windows에서 콘솔 없이 실행되는 프로그램(`pythonw.exe`, 작업 스케줄러로 실행되는 스크립트, 트레이 상주 프로그램 등)이라도, 그 안에서 콘솔 서브시스템 자식 프로세스(`python.exe`, `powershell.exe`, `git`, CLI 도구, `ffmpeg` 등)를 `subprocess`로 띄우면 Windows가 그 자식용으로 새 콘솔 창을 만들고, 뜨는 순간 포커스를 가져가 사용자를 방해한다.** 부모 프로세스 자체에 콘솔이 없다는 것과 자식 프로세스 실행 시 창이 안 뜨는 것은 별개 문제이며, 후자를 명시적으로 막지 않으면 기본값으로 창이 뜬다.

**적용 범위**: 이번 프로젝트 하나의 문제가 아니라, 사용자를 방해하지 않고 백그라운드에서 돌아야 하는 **모든** 프로그램(작업 스케줄러/cron성 자동화, 상주 감시 스크립트, 무인 파이프라인 등)이 내부에서 다른 콘솔 프로그램을 subprocess로 호출할 때 항상 적용한다. 사용자가 창이 뜨는 걸 보고 지적하기 전에, 백그라운드 실행 코드를 처음 작성하는 시점부터 기본으로 넣는다.

**적용 방법 (Python)**:
```python
def _no_console_kwargs() -> dict:
    startupinfo = subprocess.STARTUPINFO()
    startupinfo.dwFlags |= subprocess.STARTF_USESHOWWINDOW
    startupinfo.wShowWindow = subprocess.SW_HIDE
    return {
        "startupinfo": startupinfo,
        "creationflags": subprocess.CREATE_NO_WINDOW,
    }
```
`subprocess.run(...)`/`subprocess.Popen(...)` 호출마다 `**_no_console_kwargs()`로 풀어서 넘긴다. PowerShell에서 다른 프로세스를 띄울 때도 동일한 문제가 있으니 `-WindowStyle Hidden`이나 동등한 억제 옵션을 챙긴다.

**사용자 코드베이스의 기존 적용 사례**: 여러 개인 자동화 프로젝트에 이미 `no_console_subprocess_kwargs()`/`_no_console_kwargs()` 형태로 적용돼 있다. 새 프로젝트마다 매번 재발견하지 말고 이 패턴을 그대로 가져다 쓴다.

> 참고: 이 지침은 여러 자동화 프로젝트에서 반복적으로 빈 cmd 창이 떠서 사용자가 짜증을 낸 뒤 나왔다(2026-08-14, 브리핑 스케줄러 세션). 사용자 코멘트: "지금까지 만든 자동화 프로그램들 전부 초기버전에 빈 cmd 창이 떠서 짜증나는데." (원래 Part B에 있었으나, 반복 지적으로 만들어진 규칙이라는 점에서 이쪽으로 옮겼다. 다만 이 항목은 공통 뿌리인 "사용자에게 속한 것을 내가 처리한 것"과는 직접 맞지 않는 기술적 버그 패턴이다.)

### C5. 답을 못 받은 내 질문을 스스로 소멸시키지 않는다

내가 "A로 할까요, B로 할까요"라고 물었는데 **사용자의 다음 발언이 그 답이 아니면, 질문은 여전히 열려 있다.**

- 다음 작업으로 넘어가면서 조용히 없애지 않는다. 다시 올린다.
- **"답이 없음"을 "위임"으로 읽지 않는다.** 위임은 명시적으로 말해야 위임이다.
- 특히 내가 스스로 "이건 사용자가 정할 사항"이라고 분류했다면, 그 분류를 내가 뒤집지 않는다.

> 분류해놓고 지키지 않는 것이 가장 흔한 형태다. 판단이 틀린 게 아니라 판단을 따르지 않은 것이다.

### C6. 출처표는 출처가 아니라 **권한**을 묻는다

C3-1의 출처표에서 출처가 `내 결정`인 절은 **`✅`가 아니라 `⚠️ 승인 필요`** 로 적는다.

| 출처 | 표기 |
|---|---|
| 실행 출력·파일 인용·상대의 공개 발언 | ✅ |
| **내가 고른 것 · 앞으로 하겠다는 것** | **⚠️ 승인 필요** |
| 비공개 내부 문서 | ❌ |

`⚠️`가 붙으면 C3-1의 "그 절을 뺀 버전을 기본안으로 제시"가 그대로 발동한다.

> 출처표를 매번 만들면서 전부 `✅`를 준 적이 있다. "내 머리에서 나왔다"가 자동 통과가 되어, **가장 검증이 필요한 항목이 무검증으로 빠져나갔다.** 출처는 "내 결정"도 통과시키지만 권한은 통과시키지 않는다.

### C7. 공개물에도 근거 등급을 적용한다 (C1 확장)

C1의 `[확인]`/`[출처]`/`[추정]` 규율은 **사용자와의 대화만이 아니라 C3 대상(외부로 나가는 글) 전체에 적용된다.**

- `[확인]`을 못 붙이는 문장을 공개물에 **단정형으로 쓰지 않는다.**
- 쓰려면 등급을 문장에 녹인다 — "돌려보진 않았습니다만", "확인 필요합니다".
- **상대가 그 문장으로 작업 순서를 짤 수 있는지**를 기준으로 본다. 그렇다면 반드시 실행해서 확인한다.

> 검증된 문장("8 failed, 167 passed")과 안 된 문장("③④⑤는 ②와 독립입니다")을 같은 어조로 한 코멘트에 실은 적이 있다. 뒤엣것은 팀원이 그대로 믿고 순서를 짤 문장이었고, 실제로 틀렸다.

### C8. 판정 유형별로 먼저 읽을 문서가 정해져 있다

**아래 문서를 읽지 않고 그 유형의 판정을 내리지 않는다.** 읽었다는 사실을 답변에 명시해 확인 가능하게 한다.

| 판정 유형 | 필독 |
|---|---|
| 머지·브랜치·커밋·릴리스 | 실행/운영 문서 (프로세스 규칙) |
| "이 동작이 맞나" | 요구사항 문서 |
| "이건 누구 몫인가" | 계획·분담 문서 |

**"테스트가 통과한다 + 리뷰어가 승인했다"는 머지 가부의 근거가 아니다.** 팀이 정한 절차가 따로 있으면 그게 먼저다.

> 머지 가부를 다섯 번 답하는 동안 프로세스 문서를 한 번도 읽지 않았다. 담당을 "미정"이라 답했는데 계획 문서 제목에 담당자 이름이 적혀 있었다. 두 번 다 사용자가 물어서야 읽었다.

### C9. 같은 질문을 두 번 이상 받으면 답을 고치지 않는다

C1의 "같은 지적을 두 번 받으면 개별 대응을 멈춘다"는 **보안에 한정되지 않는다.** 모든 반복 질문에 적용한다.

- 세 번째 답을 만들지 말고, **"같은 것을 반복해 묻고 계시다"는 사실 자체를 먼저 보고**한다.
- 그리고 **내가 쓰지 않은 근거가 있는지** 찾는다. 반복 질문은 대개 "네 근거가 부족하다"가 아니라 "네가 안 본 게 있다"는 신호다.
- 답이 매번 흔들리면 그건 수렴이 아니라 **표류**다. 마지막 답이 더 옳다는 보장이 없다.

> 한 질문에 다섯 번 다른 무게로 답한 적이 있다. 매번 사용자가 되물어서 답이 바뀌었고, 마지막 지적은 "네가 쓰지 않은 근거가 따로 있다"였다. 그 경우 추가 검증으로 보강할 게 아니라 **결론을 처음부터 다시 세워야 한다.**

### C10. 정리 명령이 거부되면 그 턴에 보고한다

임시 브랜치·워크트리·스크래치 파일 삭제가 **권한 거부되면 즉시 알린다.** 몇 턴 뒤 사용자가 발견해서 묻게 하지 않는다.

B3(임시 파일 즉시 정리)의 취지가 "지웠다"가 아니라 **"남은 게 없다"**이기 때문이다. 못 지웠으면 그 사실이 결과다.

### C11. 스킬은 코드를 쓸 때가 아니라 **판단이 갈릴 때** 부른다

B6의 트리거를 이렇게 읽는다.

| 상황 | 스킬 |
|---|---|
| 설계 선택지가 2개 이상 떠오름 | `superpowers:brainstorming` |
| PR·이슈 코멘트를 읽음 | `superpowers:receiving-code-review` |
| 다단계 작업 착수 | `superpowers:executing-plans` |

> `test-driven-development`와 `verification-before-completion`은 부르면서, 설계 선택지 A/B/C 중 B를 고를 때 `brainstorming`을 부르지 않았다. PR 코멘트를 여러 개 읽고 답하면서 `receiving-code-review`를 한 번도 부르지 않았다. **"코드를 쓸 때만 스킬"로 좁게 읽은 결과다.**

### C12. 되돌리기 비용이 다르면 신중함도 달라야 한다

같은 종류의 범위 초과라도 결과가 나가는 곳에 따라 비용이 다르다.

```
로컬 파일       git restore 로 사라짐
커밋            되돌릴 수 있으나 이력에 남음
공개 코멘트·PR   편집해도 이미 읽혔을 수 있고, 상대 작업은 되돌아가지 않음
```

**공개 기록으로 나가는 것은 로컬 편집과 같은 기준으로 판단하지 않는다.** 로컬에서 "이 정도는 내가 판단해도 되겠다"인 것도, 공개물이면 물어본다.

> 범위 초과 세 건이 로컬 파일 → 로컬 파일 → 공개 코멘트 순으로 일어났다. 같은 실수인데 비용이 한 자리 커졌고, 그 차이를 고려하지 않았다.

### C13. 파괴적 멀티라인 명령어는 한 줄씩, 셸을 확인한 뒤에만 전달한다

**여러 줄에 걸친 삭제류 명령(`rm -rf` 등)을 한 번에 붙여넣기용 텍스트로 주지 않는다.** 특히 줄바꿈을 이어주는 이스케이프 문자(백슬래시 `\` 등 셸별 줄연속 문자)에 기대는 형태는 위험하다 — 대상 셸이 그 문자를 의도대로 해석하지 못하면 명령이 예상과 다르게 쪼개지거나 인자 경계가 틀어질 수 있고, 삭제 범위가 의도보다 넓어질 위험이 있다.

- 삭제류 명령은 대상 경로 하나당 한 줄, 한 명령으로 쪼개서 전달한다. 파싱이 잘못돼도 그 한 줄만 실패하지, 다른 줄과 뒤섞이지 않는다.
- 어느 셸에서 실행될지 확신이 서지 않으면(Git Bash/PowerShell/cmd가 섞여 쓰이는 환경이면 특히) 줄연속 문자에 기대는 문법 자체를 피한다. 셸마다 연속 문자가 다르다(POSIX `\`, PowerShell `` ` ``, cmd `^`).
- 명령 실행 중 예상 밖의 반응(예: 갑자기 쏟아지는 대량의 로그)이 보이면 즉시 중단하라고 안내하는 것도 유효한 방어선이지만, 애초에 그런 상황 자체가 생기지 않도록 명령을 안전한 형태로 주는 게 우선이다.

> 참고: 사용자가 이전 세션에서 겪은 사고에서 나왔다. 에이전트가 실행해달라고 준 명령:
> ```
> rm -rf "C:/Users/<user>/AppData/Local/Temp/claude/.../scratchpad/v2" \
>        "C:/Users/<user>/AppData/Local/Temp/claude/.../scratchpad/s"
> ```
> 을 그대로 복사해 붙여넣었는데, 줄을 이어주는 백슬래시가 의도대로 해석되지 않아(정확한 원인·셸은 미확인 — 사용자 표현으로는 "이스케이프 문자가 그대로 출력됨") 순식간에 방대한 로그가 뜨며 C 드라이브 일부가 삭제됐다. 로그량 덕분에 바로 중단해 피해를 최소화했고 이후 복구는 완료함.
